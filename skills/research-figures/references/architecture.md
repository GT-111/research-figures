# Editable architecture and slide delivery

## Scientific topology

Name the message first. Identify the core contribution and its necessary relations, then source/reference inputs, state/history, modules, objectives, outputs and feedback where they actually occur. Associate important nodes and edges with project evidence in the brief. Keep future targets outside causal inputs. Distinguish a designed interface from a validated application.

A teaser communicates the problem and contribution through examples and compact evidence. A framework communicates how interfaces fit. A mechanism figure exposes what is new with local tensor/geometry/network illustrations. Appendix figures resolve detail that would crowd the framework. These roles do not prescribe a model topology or fixed panel count.

## Runtime authoring, no bundled exporter

This skill is documentation only. On invocation, choose the available native authoring environment and write the small amount of project-local code required by the specific master. Resolve bundled workspace libraries when the host provides them. Reasonable options include a native slide API, PptxGenJS, python-pptx or direct OOXML; choose based on installed capabilities and the needed geometry. Draw.io can be authored as native mxGraph XML. Matplotlib is the default numerical renderer.

Keep authoring code, figure specs, scene/map records and generated output in the project's ignored/external figure directory. Do not create a mandatory universal renderer, stable scene schema, package installation or reusable module inside this skill. A project-local helper is useful when several figures share repeated primitives; it should serve that figure set, not determine the layout. The generated master is the composition source.

## Object structure and geometry

Read [connector-design.md](connector-design.md) when the figure contains connected computation, conditioning, training or return paths. Choose their producer/consumer ports and reserve route space alongside module layout.

Reconstruct each semantic region from the master. Use native rectangles/freeforms for modules, polygons for trapezoidal mappings, text boxes for short labels and connectors for relationships. Keep stable meaningful object names so revisions can target a module or label. Group a module, internal motif and label when the authoring environment supports it; avoid grouping an entire figure into one uneditable visual object.

Choose a common logical design canvas (e.g. 1600×900), then scale uniformly into the presentation. Keep compact paper bounds separately. Set explicit font, weight, text alignment and margins rather than inheriting a presentation theme. Disable automatic text shrink-to-fit; fit short labels into their intended bounds. If a LibreOffice render still centers an explicitly left-aligned label, inspect inherited text-body autofit and horizontal centering (`anchorCtr`) as well as paragraph alignment; verify the final render after correcting them. Use independent captions rather than drawing paragraphs inside modules. Place a connector caption in its actual free corridor, including its full rendered width; moving it outside a box is insufficient if it overlaps the next box or route. Break a long header at a meaningful phrase or widen its region while preserving the contribution hierarchy. Inspect the longest repeated-stage title and narrowest output label before copying their styling.

Use editable freeform paths for irregular contours; native curve segments or enough smooth points can approximate the sketch stroke. Keep trapezoid direction meaningful to compression/projection/expansion. Native sketch effects are optional when the target renderer supports them; inspect the actual result. Do not rasterize basic shapes merely to obtain a rough line. Match colored header bands to the containing rounded/irregular boundary; rectangular fills must not cover or protrude past its corners. Keep the structural contour above the fills. After grouping, recheck the group's order relative to stage backgrounds and frames in each renderer; grouping can move an entire body behind a later opaque container even when its internal layer order is correct. Approximation of dry-ink texture is acceptable, but retain the chosen contour character with native bowed paths where the design calls for it.

Use the single native connector and built-in line-end treatment specified in [connector-design.md](connector-design.md). Reserve arrow corridors before reconstructing details. Inspect visible head direction as well as attachment, especially for leftward connectors: repair an observed orientation/line-end issue at the connector instead of replacing normal arrows with segmented shafts and separate polygons. Avoid arbitrary custom connector XML that has not been opened in a native renderer. For a returning or multi-bend route, prefer supported preset elbow geometry and its adjustment handles. A custom path placed inside a connector object can be discarded or reinterpreted by the importer even when the XML is valid. Prototype the actual leftward/upward return orientation and bend sequence the figure needs; a successful rightward straight arrow does not exercise that case. If a preset cannot express the route, apply the documented continuous-path exception and disclose its attachment limitation.

## Draw.io-specific details

Use native mxCell vertices, edges, editable labels and grouping. Keep editing IDs/group metadata separate from visible `value` labels; groups carry no display text unless an intentional caption needs it. Match label mode to content: HTML breaks require `html=1`, while plain labels use tested native line breaks. Literal markup and internal group names must not leak into the rendered figure. An mxfile needs its normal root cells and a diagram per figure. Give edges source/target IDs and explicit anchor or waypoint geometry as appropriate. Keep image assets self-contained and preserve aspect ratio. Semicolons in image data URIs can be interpreted as style delimiters; use a supported URL-encoded SVG or tested image encoding rather than assuming a browser data URI survives an mxGraph style string.

Treat sketch contours and interior fills as separate choices. Native sketch presets can replace a solid fill with hatching; white text then becomes unreadable and the deep palette disappears. For the native sketch renderer, explicitly set `fillStyle=solid` when a solid deep fill is intended; automatic fill selection can choose hachure for saturated colors. For intended hatching, retain an explicit native hatch layer with solid label backing. Alternatively use an ordinary solid native body plus a separate irregular native contour. Inspect a representative deep module with its label in the actual renderer before repeating the style across the scene.

Custom stencil payloads require the renderer's actual encoding: diagrams.net Graph.compress uses URI-encoded XML, raw DEFLATE and then base64. A zlib-framed plain XML buffer can silently fall back to a rectangle. Verify the actual rendered outline, not just the XML.

A stencil/freeform object is editable at object geometry level; an embedded SVG icon is a movable/scalable image unless paths are explicitly rebuilt. Do not describe those editability levels as identical. Confirm the actual installed renderer's page-index convention before selecting a page.

## PowerPoint-specific details

Basic geometry/text/connectors are native shapes. Photographs, model renders, official logos and numerically rendered panels are independent picture/vector objects. Their pixels are not native module geometry. Preserve proportions and relationships among native subobjects. Preserve deliberate shadows, patterns and depth using [native-style-reconstruction.md](native-style-reconstruction.md). Clear only unwanted inherited shadows or theme colors; disabling theme effects does not permit removing designed shadow objects. With direct OOXML/python-pptx authoring, an empty `a:effectLst` alone may leave a theme shadow active in LibreOffice; the shape style's `a:effectRef` may also need `idx="0"`. Verify the rendered result rather than assuming a library's no-shadow flag covers inherited effects.

A complete PPTX package includes all media relationships. If assembling existing slides, preserve image/chart/hyperlink/notes relationships that occur in those inputs; use an appropriate native library/API rather than copying XML without its referenced parts. Keep shared slide dimensions explicit. If importing a different canvas, normalize uniformly and verify apparent native type/ink size: a group transform can scale geometry while the renderer keeps font sizes, stroke widths and text margins absolute. Scale those physical metrics when needed, preserving the source hierarchy and picture aspect rather than only fitting the outer group bounds. Test a representative module movement and label change on a copy of the final current deck, then render the edited copy. Confirm both content and style survive saving; an edit trial from an earlier export does not validate the delivered file. State whether connectors follow automatically or need manual rerouting.

## All figures in one PPTX

Accept the plain-language request directly. Inventory requested figures and preserve explicit order; otherwise use main figures followed by appendix and result pages. Reuse existing editable architecture slides. Insert quantitative panels with their vector/data/code sources retained separately. A clean slide can contain a native title, task photos and result panels; no demand to convert a plot into a native PowerPoint chart.

Read the latest user-edited deck before assembly. Preserve its objects and edits. Avoid regenerating it from stale source code. PPTX and draw.io are parallel deliverables with independent later edits; do not promise automatic two-way synchronization.

## Native render verification

Open/render the actual PPTX with PowerPoint or LibreOffice and the actual draw.io with diagrams.net/draw.io Desktop. For headless environments, a temporary LibreOffice profile and virtual display can help. Concurrent figure jobs need separate application profiles and output paths; draw.io Desktop may otherwise hand an export to an already-running instance. Use a job-local user-data directory when parallel native exports share the host. Compare the renders with the master and with each other for labels, scientific topology, assets, hierarchy and clipping. XML or ZIP validity is not visual verification.

When a native renderer is unavailable, deliver the editable artifact if usable but disclose that its native appearance was not checked. Keep real previews and any observed approximation in the project brief. A clean export is not proof of stylistic success; preserve the generated master correspondence.
