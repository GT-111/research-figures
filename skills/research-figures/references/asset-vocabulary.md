# Prepared asset vocabulary

Read when preparing a reusable material kit or choosing visual carriers for a new figure. This document owns grouped motif presets. Base geometry, palette and fonts remain in their existing owners. Genuine media sourcing and evidence pairing remain in assets-and-composition.md.

## Preset the drawing language

Prepare reusable native groups with resolved ink, type and palette roles. The installed skill stores their recipes; optional PPTX/draw.io/SVG specimens and cached media live in a separate user/project material directory. They are conveniences, not a required installed library, machine path or exporter. The invoking agent can rebuild the relevant preset using task-specific code. A user-edited specimen remains authoritative for its next revision.

Discover existing materials from the user's supplied catalog, the figure brief or project assets. A host may also provide an optional user-level `research-figures-materials/catalog.md` beside its `skills/` directory; inspect that catalog when present. It identifies genuine media, provenance and available visual specimens without tying the skill to a project. If absent, source/render only the materials the current figure needs. Reuse an applicable motif's visual ingredients, then instantiate its project facts and current connector rules; a cached example is not authority for mechanism assumptions or a legacy exporter workaround.

Useful first presets:

| Preset | Independently editable ingredients | What it can express |
|---|---|---|
| Token / feature strip | Regular cells, continuation dots, short variable/dimension label | Sequence, vector or latent carrier; counts are exact or explicitly schematic |
| Availability / attention mask | Matched cell rows, active/inactive property marks, selection overlay | An actual selection/support pattern, without inventing attention topology |
| Noisy / clean carrier | Same geometry with separate hatch layer or clean fill | Representation state; conditioning/generated role is labeled separately |
| Temporal frames | Independent image slots, timestamp labels, stack/sequence bracket | Actual temporal support; blank slots contain no fictional task imagery |
| Matrix / operator / result | Regular matrices, multiplication/transpose markers, output carrier | A meaningful linear/relation operation when the method uses it |
| Condition / clock | Compact state label, clock/timeline cue and conditioning port | Availability or update time with an explicitly named clock |
| Read / update / next state | Current state carrier, actual update operator, next-state carrier | Iteration or memory mechanics, not an automatic controller assumption |
| Learning annotations | FROZEN label, native snowflake cue, stop-gradient slashes, update/EMA label | Distinct parameter and gradient facts on the actual owning path |
| Combining operators | Small sum, selection or gate symbol with named input/output ports | Addition, selection or gating only when supported by the method |
| Sharing / focus links | Bracket, association line, zoom boundary | Shared parameters or an expanded detail, without suggesting computation |
| Styled module shell | Solid body, bowed contour, header, shadow, sparse hatch and label backing | Reusable ink treatment, with different roles supplied by project content |
| Relation specimen | Horizontal/vertical and orthogonal elbow relations, fixed ports, branch/crossing examples, receiving head | The connector language in connector-design.md |

Make light-body/dark-header and plain/hatched/dashed variants using the resolved palette. Vary only the property the variant encodes. Keep shapes regular where numeric or spatial geometry matters. Use nominal sizes and short labels with enough free space for the motif; do not bake a specific model name, tensor dimension, loss or pipeline into a preset.

Group the body and its designed contour/shadow/label/motif, while keeping contents individually editable. Connection sites belong to meaningful inputs/outputs. Decorative hatch strokes are not relation edges. Preset selection should shorten authoring, not turn every method into the same layout.

## Build operation motifs from those ingredients

A token strip inside a named box is a carrier, not an explanation of a mechanism. Choose the intermediate state or operator that makes the contribution intelligible, and build a small local motif around it. The following are transferable examples learned from original method figures; use only relations supported by the current project. Keep source-paper identities and the inspected figure/caption in the project brief.

For canonical mapping, correspondence, fixed/shared representations, distributions and heterogeneous specifications, read [representation-motifs.md](representation-motifs.md). For fixed scalar grids, learned entries, index restoration, residual quantization and codec objectives, read [quantization-and-codec-motifs.md](quantization-and-codec-motifs.md). For sparse routing, autoregressive history, aligned tracks, component hierarchies or streaming readiness, read [sequence-and-routing-motifs.md](sequence-and-routing-motifs.md). These extend the vocabulary by explanatory operation, without requiring a model-family template.

**Selection or support.** Align the input, controlling mask and output by the actual indexed entity. Show the operation that changes participation and preserve position/order when the method does. Exclusion, zero multiplication and replacement by a learned token differ; label the actual inactive convention. Hatching can denote inactive support without asserting a measured zero. Availability and attention support are different facts.

**Memory attention.** Show who supplies queries and who supplies keys/values. If a read-only memory provides K/V, branch it into those projections while the querying stream supplies Q; feed them independently into the attention operation. A Q-by-K matrix can explain support, followed by its weighted-value output. Query/key/output counts must agree even when the specimen is schematic. Do not draw K into the Q projection, chain K into V, or add a decorative memory write loop. When writing is the contribution, expose the real write operation and next-memory carrier locally.

**Additive correction.** Reuse the same input at a visible branch, show the base path and the correction path, then combine their outputs with the actual operator. For a low-rank linear correction, compression → rank carrier → expansion explains more than an adapter label. Supply dimensions, scale and parameter ownership. Other residuals may correct actions, features, forces or state estimates; their combine operation and deployment behavior come from the project rather than this motif.

**Iterative state change.** Distinguish prediction from update. A predictor emits its predicted quantity; the scheduler/solver consumes that quantity and the current state to produce the next state. The return and final exit belong to that update. Name the clock and active/held quantities. In an overview, a compact repeat-model-and-update inset can own the iteration instead of several full-page loops. An expanded mechanism shows the actual scheduler inputs when that detail explains the contribution.

**Relational supervision.** Use matched student/target branches, their features and the actual comparison operation before the objective. A feature inner product, pairwise relation matrix and feature equality communicate different objectives. Show the objective's update recipient; omit optimizer plumbing that the caption can explain. Frozen parameters, stop-gradient and an EMA target are independent facts with different annotations.

**Shared carrier, separate readouts.** Branch one representation into the actual readout operations and expose their distinct queries or heads when that difference matters. Shared tokens do not imply shared readout weights. A future/delta target equation can sit beside the motif without creating a false prediction-to-prediction dependency or recurrence. Supply the horizon, target definition and training/deployment availability.

Keep these mechanisms local and select the few visible relations that explain them. Port ownership can remain native attachment metadata; Q/K/V or a named state label is useful explanation, whereas an interface glyph at every anchor adds wiring noise. Preserve regular cell geometry and consistent counts for the operation; apply bowed contours, depth and hatch to its surrounding visual language. The current method may need a new motif: derive it from the transformation and compare it with an original-paper illustration rather than forcing it into this list.

## Prepare genuine media separately

The most useful physical kit contains morphology/identity reference views: a few hands, grippers, arms, full bodies or sensors that recur in the user's work. Prefer actual project meshes and authoritative model-gallery renders. Record model/version, source, license and what the image demonstrates. Use a consistent view and apparent size when comparing embodiments; a gallery thumbnail cannot determine joint values, contact geometry, scale or task success. Render the project model when those details matter. Extra views require the mesh or genuine photographs, not a fabricated reconstruction of a single thumbnail.

For reusable insertion, prefer newly rendered transparent RGBA assets from genuine geometry, plus white/warm-background previews. Remove checkerboard floors, skyboxes, axes and unrelated scene props from the rendering scene; do not keep a simulator's dark gallery background as the universal visual style. Preserve materials unless a neutral rendering is explicitly selected. Use an object/segmentation pass or native alpha output to obtain the silhouette, with real holes between fingers/links retained. Inspect alpha on light and darker fields for cut edges, opaque corners, halos and missing parts. Avoid AI reinterpretation of hardware to manufacture a cutout. Record view and pose parameters with the source and license.

An identity kit can hold official vector marks, light/dark approved variants and plain typographic fallback names for recurring backends/benchmarks/datasets. Keep real marks in their original proportions/colors. A favicon is identified as an icon; a parent-company mark is identified as such. If no authoritative mark is available, retain the name rather than inventing one. The list of actual identities and source URLs stays outside the generic skill.

Fonts can be resolved/cached once for a figure set from a legitimate source; preserve redistribution terms when shipping them. Font specimen and installation requirements follow palette-and-type.md. Do not create a new type choice for each asset card.

## Composition pieces and exact results

Prepare empty task-image rows, before/after pairs, zoom callouts, contact/trajectory-overlay groups, qualitative grids and plot-plus-image slots with native headings/brackets. Their images, timestamps, coordinate frames and metric cohorts are filled from the actual project. A task frame, morphology reference and benchmark identity are different asset roles.

Plot presets are style recipes and layout specimens: bar/line/overlay/band/heatmap/table anatomy, method color/marker/hatch mapping and axis/legend placement. Rebuild every numerical mark from its actual data. A prepared curve or uncertainty swatch is not a result, and a blank slot is not zero. Retain minimal redraw code and the data references with the project's result assets.

For an initial kit, prioritize a small selection that demonstrates these roles and current style. Expand when a real project needs another carrier or identity. Do not bulk-download model collections or bake a paper's complete figure into a universal template. Keep genuine media, native motif sources, previews and attribution readable as separate materials.
